Concepts

The Silo mental model.

A project selects a workspace. The image supplies the tools. Sessions decide how long a container lives, while binds, managed state, and an environment allowlist decide what else crosses the boundary.

Projects are the unit of identity

Every command that runs a container starts by resolving the current directory to a canonical path and discovering a project root:

  1. The nearest ancestor containing a .silo.toml file wins as an explicit Silo boundary.
  2. Without a Silo marker, Silo asks Git for the top-level working tree with git rev-parse --show-toplevel. Git therefore handles normal repositories, linked worktrees, and submodules itself.
  3. If Git is unavailable or does not report a valid ancestor, the exact current directory is the project.

That root is what gets mounted, and it is what later sessions reuse. Two folders with the same name stay separate when their full paths differ.

Drop a .silo.toml in a directory when you want that directory, rather than the Git root, to be the project. Silo cannot use /, or a path that is not valid UTF-8 or that contains ,, =, or a newline.

Images are built in two layers

silo image build publishes a base image, then a tool image on top of it. The base contains everything Silo needs to run a session: the silo user, shells, Homebrew, and the programs that start commands and host ports.

The default tool image adds a small extras layer and is published as silo:latest. What it installs is in silo-extras.dockerfile. A configured image.dockerfile replaces that layer. silo image update rebuilds it on the base you already have. After upgrading Silo, run silo image build so the base matches the new binary.

Sessions and containers are different

A session is the interactive shell or command you asked Silo to run. A container is the Linux environment hosting it. Shared mode lets several sessions occupy the same project container; isolated mode gives one session a new container.

Shared means several commands for the same project can see each other's processes and temporary files. A different project always gets its own container. silo start keeps the shared container up while it is idle. silo stop shuts it down.

Files you create belong to your Mac user

Inside the container you are the user silo, with home /home/silo. The project is mounted at /home/silo/ plus the directory name, and that is the working directory.

Silo maps that user to the Mac account that launched it, so new files in the project, in a writable bind, or in managed state belong to you. Files that were already there keep their existing owners.

State has an explicit lifetime

The project root is always a host bind and therefore survives every container. Binds and managed state make the lifetime and ownership of other data explicit:

ConfigurationSourceTypical use
bindsAn existing host directory, with explicit accessDocuments, local output, or data owned outside Silo
state.projectPrivate Silo-managed storage keyed by project and nameBuild caches and dependencies that should not cross projects
state.userPrivate Silo-managed storage keyed by nameAgent credentials or tool state intentionally reused across this user's projects

Every bind declares access = "read-only" or access = "read-write". Managed state is always writable. Relative targets beginning with ./ anchor to the project directory; ~/ anchors to the Silo user home; absolute targets stay absolute.

Managed state lives under $XDG_STATE_HOME/silo/state when that variable is an absolute path, and under ~/.local/state/silo/state when it is unset, empty, or relative and HOME is absolute. Use silo state to inspect it and silo state delete to remove an unused entry safely.

Environment is an allowlist of names

Silo does not copy your shell environment into the container. env_vars names the variables to bring in, such as OPENAI_API_KEY. The value is read from the terminal that creates the container, and it is not written into config or into Silo's own output. A project list replaces the global one.

A session that joins a container already running keeps the values from when it was created. Stop it and start again after you change a name or a value. HOME, PATH, SHELL, BREW_PREFIX, and names beginning with SILO_ are reserved. Inside a session, HOME is /home/silo.

Choose which project paths tools may change

The whole project tree is mounted read-write so editors, builds, formatters, and agents can change working files. By default, Silo overlays an existing .git or .jj directory read-only; tools can inspect repository metadata without changing it.

Projects that expect containerized tools to manage repository metadata can remove those paths or disable the workspace.read_only overlays. Other project directories can be protected with the same literal, project-relative list:

workspace.read_only = [".github"]

workspace.read_only = [] turns the overlays off. Missing paths are skipped, so a shared config can mention directories some projects do not have. A file, a broken symlink, or a path that leaves the project is skipped with a warning. Silo also refuses a writable bind or state mount that would cover a protected path or hide it.

A read-only .git does not hide .github. Silo remounts neighboring directories whose names start with the protected directory's name, so they stay visible and writable.

Overlays can only cover directories. A skipped entry protects nothing.

Custom images extend the Silo contract

Setting image.dockerfile replaces the default extras layer, not the runtime foundation. The configured Dockerfile must explicitly use this literal base reference:

FROM silo-base:latest

USER silo
# Add the project-specific tools you need here.
RUN brew install go
USER root

The Dockerfile needs exactly one stage, and that FROM line has to be literal. Silo rewrites it so the name is not looked up in a registry. The file's directory is the build context. Because this replaces the extras layer, reinstall Codex, Claude Code, or anything else from the default image that you still want.

A custom Dockerfile is trusted. Keep the silo user, entrypoint, and shells working. Silo checks those on startup and leaves the rest to you.
