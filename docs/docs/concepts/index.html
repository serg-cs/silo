Concepts

The Silo mental model.

A project selects a workspace. The image supplies the tools. Sessions decide how long a container lives, while binds and managed state decide which data outlives it.

Projects are the unit of identity

Every command that runs a container starts by resolving the current directory to a canonical path and discovering a project root:

  1. The nearest ancestor containing a .silo.toml file wins. An explicit Silo marker takes precedence over every VCS directory in the ancestor chain.
  2. Without a Silo marker, the nearest ancestor containing a real .git or .jj directory becomes the root.
  3. Without either marker, the exact current directory is the project.

The canonical root determines the mounted source tree, the container working directory, the shared container ID, project-scoped state, and ownership labels. Two directories with the same basename remain separate projects when their canonical paths differ.

Put an empty or partial .silo.toml at a monorepo boundary when you want Silo's project root to differ from the VCS root.

A stable base supports replaceable tool layers

silo image build first creates silo-base:latest. This Ubuntu-based image owns the stable Silo contract: the silo user, supported shells, Homebrew, sudo, SSH forwarding server, supervisor, session helpers, entrypoint, and required filesystem paths.

Silo then builds one derivative. Without image.dockerfile, the embedded extras Dockerfile produces silo:latest with:

  • Codex, Claude Code, and many other coding-agent CLIs.
  • Bash, Zsh, Fish, and Nushell, with the host's supported $SHELL mirrored automatically and Zsh as the fallback.
  • Rust, Node.js, Python, uv, Ruff, Playwright with Chromium, GitHub CLI, Jujutsu, and common linters.
  • Practical terminal tools including Ripgrep, fd, fzf, jq, just, tmux, Helix, Vim, lazygit, Yazi, and Zoxide.

A configured Dockerfile replaces only that extras layer. It must have exactly one stage beginning with a literal FROM silo-base:latest. Silo runs the actual entrypoint and a small compatibility smoke test before publishing the derivative's deterministic local tag.

Rebuilding is explicit. One fresh builder first produces the base without cache, then the derivative reuses those completed base-stage layers and installs only its additions. Silo embeds the base under an internal stage name, so the published silo-base:latest tag is never resolved as a derivative input. Silo serializes builds because Apple's builder is user-global, stages each result before replacing its stable tag, cleans stale builder storage, and prunes dangling images after the build.

Sessions and containers are different

A session is the interactive shell or command you asked Silo to run. A container is the Linux environment hosting it. Shared mode lets several sessions occupy the same project container; isolated mode gives one session a new container.

PropertySharedIsolated
Requested bysilo runsilo run --isolated
Container IDStable digest of the project pathUnique to the Silo process
ConcurrencyMultiple overlapping sessionsOne foreground session
Exit behaviorStops after the final lease closesStops and is deleted
Best forNormal development and cooperating agentsClean-room work and throwaway checks

Shared does not mean global: one project never joins another project's container. It means that multiple commands for the same canonical project can share running processes and ephemeral container state while their sessions overlap.

State has an explicit lifetime

The project root is always a host bind and therefore survives every container. Binds and managed state make the lifetime and ownership of other data explicit:

ConfigurationSourceTypical use
bindsAn existing host directory, with explicit accessDocuments, local output, or data owned outside Silo
state.projectPrivate Silo-managed storage keyed by project and nameBuild caches and dependencies that should not cross projects
state.userPrivate Silo-managed storage keyed by nameAgent credentials or tool state intentionally reused across this user's projects

Every bind declares access = "read-only" or access = "read-write". Managed state is always writable. Relative targets beginning with ./ anchor to the project directory; ~/ anchors to the Silo user home; absolute targets stay absolute.

Managed state lives below $XDG_STATE_HOME/silo/state, or ~/.local/state/silo/state when XDG_STATE_HOME is unavailable. Use silo state to inspect it and silo state delete to remove an unused entry safely.

Choose which project paths tools may change

The whole project tree is mounted read-write so editors, builds, formatters, and agents can change working files. By default, Silo overlays an existing .git directory read-only; tools can inspect Git repository state without changing its metadata.

Jujutsu metadata remains writable because even inspection commands acquire locks and may update .jj. Adding .jj to workspace.read_only prevents normal Jujutsu operation.

Projects that expect containerized tools to manage repository metadata can remove that path or disable the workspace.read_only overlays. Other project directories can be protected with the same literal, project-relative list:

workspace.read_only = [".github"]

Use workspace.read_only = [] instead to disable every read-only project overlay. Separately configured binds retain their own access modes.

A read-write bind that overlaps a protected path can make it writable again, and Silo warns when it detects that overlap.

Read-only overlays cannot target individual files because Apple container accepts only directories as bind-mount sources.

Custom images extend the Silo contract

Setting image.dockerfile replaces the default extras layer, not the runtime foundation. The configured Dockerfile must explicitly use this literal base reference:

FROM silo-base:latest

USER silo
RUN brew install protobuf
USER root

Silo replaces that reference with an internal stage before building, which prevents any registry lookup for silo-base:latest. ARG-based base references and additional local stages are rejected. External images may still be used by instructions such as COPY --from=registry.example/tools:latest. Silo preserves the configured directory as the context and gives each Dockerfile, effective build context, and Dockerfile-specific ignore selection a deterministic local image tag. This keeps shared Dockerfile contents from colliding when projects supply different relative COPY inputs or ignore rules.

A custom Dockerfile is trusted input. Keep the inherited silo user, entrypoint, lifecycle helpers, supported shells, and expected paths intact. Silo catches basic startup incompatibilities, but does not police permissions, links, package changes, or every way root-level build instructions can break later sessions.
