Concepts

The Silo mental model.

A project selects a workspace. The image supplies the tools. Sessions decide how long a container lives, and mounts decide which state outlives it.

Projects are the unit of identity

Every command that runs a container starts by resolving the current directory to a canonical path and discovering a project root:

  1. The nearest ancestor containing a .silo.toml file wins. An explicit Silo marker takes precedence over every Git directory in the ancestor chain.
  2. Without a Silo marker, the nearest ancestor containing a real .git directory becomes the root.
  3. Without either marker, the exact current directory is the project.

The canonical root determines the mounted source tree, the container working directory, the shared container ID, project-scoped state, and ownership labels. Two directories with the same basename remain separate projects when their canonical paths differ.

Put an empty or partial .silo.toml at a monorepo boundary when you want Silo's project root to differ from Git's root.

One image supplies the environment

silo image build creates the local OCI image silo:latest. Unless configuration selects a custom Dockerfile, Silo builds its embedded Ubuntu-based development image.

The built-in image includes:

  • Codex, Claude Code, and many other coding-agent CLIs.
  • Bash, Zsh, Fish, and Nushell, with the host's supported $SHELL mirrored automatically and Zsh as the fallback.
  • Rust, Node.js, Python, uv, Ruff, Playwright with Chromium, GitHub CLI, Jujutsu, and common linters.
  • Practical terminal tools including Ripgrep, fd, fzf, jq, just, tmux, Helix, Vim, lazygit, Yazi, and Zoxide.

Rebuilding is explicit and uncached. Silo serializes builds because Apple's builder is user-global, cleans stale builder storage, and prunes dangling images after the build.

Sessions and containers are different

A session is the interactive shell or command you asked Silo to run. A container is the Linux environment hosting it. Shared mode lets several sessions occupy the same project container; isolated mode gives one session a new container.

Requested bysilo runsilo run --isolated or any custom image

Shared does not mean global: one project never joins another project's container. It means that multiple commands for the same canonical project can share running processes and ephemeral container state while their sessions overlap.

State has an explicit lifetime

The project root is always a host bind mount and therefore survives every container. Additional named mounts let you choose where other state lives:

Mount typeSourceTypical use
HostAn existing host directoryDocuments, local output, or data owned outside Silo
ProjectPrivate Silo-managed host storage keyed by project and nameBuild caches and dependencies that should not cross projects
SharedPrivate Silo-managed host storage keyed only by nameAgent credentials or tool state intentionally reused by projects

Host mounts default to read-only and may opt into writes. Managed mounts are writable. Relative targets beginning with ./ anchor to the project directory; ~/ anchors to the built-in container home; absolute targets stay absolute.

Managed state lives below $XDG_STATE_HOME/silo/mounts, or ~/.local/state/silo/mounts when XDG_STATE_HOME is unavailable. Use silo mounts to inspect it and silo mounts delete to remove an unused mount safely.

Choose how tools access Git metadata

The whole project tree is mounted read-write so editors, builds, formatters, and agents can change working files. By default, Silo overlays the project's real .git directory read-only; tools can still inspect the index, refs, history, and worktree status.

Projects that expect agents or other containerized tools to stage, commit, switch branches, or otherwise manage the repository can enable Git metadata writes:

read_only_git = false

This setting does not change source-file access. A writable named mount that overlaps .git can also make metadata writable, and Silo warns when it detects that overlap.

Custom images keep their own contract

Setting image.dockerfile changes more than the packages. Silo preserves the image's user, entrypoint, command, and filesystem expectations instead of injecting the built-in supervisor and /home/silo contract.

  • Custom-image runs always use the isolated lifecycle.
  • Project and shared managed mounts are skipped because Silo cannot safely grant the image user access to private host-owned storage.
  • Enabled host mounts remain available, but their target must be project-relative or absolute; ~/ has no Silo-defined meaning for a custom image.
  • The project root and configured Git metadata overlay remain available.

A custom Dockerfile is therefore an environment escape hatch, not a drop-in extension of the built-in shared image.
