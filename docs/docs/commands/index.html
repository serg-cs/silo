Commands

Command reference.

Syntax, options, aliases, and examples for every command exposed by Silo.

Overview

Run Silo from the project you want to work on. The command name selects a built-in operation; an unrecognized name can select a configured quick command.

silo config, silo containers, and silo state print a readable list. Add list --json when you want JSON. Errors and warnings go to stderr and start with error: or warning:.

silo runOpen a session or run a command. silo start / stopControl a persistent shared container. silo imageBuild, update, or edit the workspace image. silo configInspect and manage configuration. silo containersInspect or delete Silo containers. silo stateInspect or delete managed state. silo <name>Run a configured shortcut.

Help and version

silo --help
silo <command> --help
silo help <command>
silo --version

The help generated by the installed binary is authoritative for that version of Silo.

Run sessions and commands

silo run

Session command
silo run [--isolated] [--cpus <count>] [--memory <size>] [--sudo] [-- <command>...]

Opens the shared container for the current project. With no command, Silo starts the configured interactive shell. Arguments after -- run as an exact command inside the workspace.

Options

--isolated
Use a new one-shot container that is removed when the session ends.
--cpus <count>
Override the configured positive CPU count for this invocation.
--memory <size>
Override the configured memory using Apple container syntax, such as 4G.
--sudo
Grant the selected image's silo user passwordless sudo access for this invocation.
-- <command>...
Run the command and arguments inside the container instead of opening a shell.

Examples

silo run
silo run -- cargo test --workspace
silo run --isolated -- ./scripts/check.sh
silo run --cpus 8 --memory 12G -- cargo build
silo run --sudo -- apt-get update

The separator is required. silo run cargo test is not a command Silo understands.

CPU, memory, sudo, and env_vars apply when the container is created. Joining one that is already running leaves those settings as they are. Stop it and start again to pick up a change.

Keep a shared container running

silo start

Persistent lifecycle command
silo start [--cpus <count>] [--memory <size>] [--sudo]

Starts the current project's shared container in the background and keeps it running between sessions. If a shared container is already running, this command promotes that instance without recreating it.

silo stop

Persistent lifecycle command
silo stop [--force]

Stops the current project's shared container. The command succeeds when no container exists and does not remove configured managed state.

Options

start --cpus <count>
Override the positive CPU count when creating a new container.
start --memory <size>
Override memory when creating a new container.
start --sudo
Enable passwordless sudo when creating a new container.
stop --force
Terminate active sessions instead of refusing to stop.
silo start
silo run -- cargo test
silo stop

Without --force, silo stop refuses to interrupt an active session or session handoff. As with silo run, creation overrides do not change an already-running container.

Build, update, or edit the image

silo image build

Image command
silo image build

Build and validate the runtime base followed by the selected derivative. With no image.dockerfile, Silo publishes its embedded extras image as silo:latest; configured Dockerfiles receive a deterministic local tag.

Builder cleanup is user-global: silo image build force-deletes Apple's current builder, so coordinate that command with any direct use of Apple Container. After publication, Silo deletes only the reclaim tags for the previous Silo base and derivative this build replaced; it does not prune other dangling images. Builds also consume ubuntu:latest, Homebrew HEAD, and current formulae; identical Silo source is not guaranteed to rebuild identically later.

silo image update

Image command
silo image update

Rebuild and validate the selected tool layer on the existing local silo-base:latest. With no image.dockerfile, Silo republishes its embedded extras image as silo:latest. A configured Dockerfile keeps its deterministic local tag. The base tag, running containers, and Apple's builder stay in place.

silo image edit

Image command
silo image edit

Open the Dockerfile selected by image.dockerfile in $VISUAL, then $EDITOR, then vi. When image.dockerfile is unset, print a message and leave the embedded extras image unopened. The command does not create a file or build an image.

Update builds that tool Dockerfile with --no-cache and without --pull. FROM silo-base:latest names the published local image. Silo inspects that tag first and stops when it is missing, before a resolver can look for it in a registry. Homebrew formulae come from the taps already stored in the base. After a Silo upgrade, or whenever the runtime base itself should be recreated, run silo image build.

Silo starts Apple's container system when necessary and serializes concurrent Silo image builds and updates. See image build and publication for the authoritative no-cache, base-and-extras, staging, validation, and cleanup lifecycle.

See image configuration for custom Dockerfiles, CPU, memory, and sudo settings.

Inspect and edit configuration

silo config without a subcommand behaves like silo config list.

silo config list [--json]Alias: ls
Print the merged configuration as TOML, or as JSON with --json. Settings that still match the built-in defaults are left out. The workspace table is always included.
silo config edit
Open the active project configuration, or the global file when no project file exists.
silo config edit --global
Always open or create the global configuration.
silo config default
Print the bundled starter configuration without reading project or filesystem state.
silo config path
Print the active configuration files, global first, then the project file. When neither file exists, report that the built-in defaults are in use.
silo config check
Run the full side-effect-free preflight, including custom-image rules and host filesystem resolution.

Editing uses $VISUAL, then $EDITOR, then vi. Silo reloads and validates the effective configuration after the editor exits; unknown keys are errors.

Common inspection flow

silo config path
silo config list
silo config list --json
silo config check

silo config check works without a project file in an ordinary directory, but rejects filesystem root / because it cannot serve as a workspace. See validation and diagnostics for the exact contract, and the configuration reference for the complete schema and merge behavior.

Manage containers

silo containers without a subcommand behaves like silo containers list.

silo containers list [--json]Alias: ls
List Silo-owned containers with their id, shared or isolated type, state, and project path. --json prints the same fields. An empty list says No Silo containers.
silo containers delete <selector> [--force]Alias: rm
Stop and delete exactly one Silo container selected by its exact ID or an unambiguous project basename.

Examples

silo containers
silo containers list --json
silo containers delete my-project
silo containers rm silo-a0b1c2d3e4f5678901234567 --force

Without --force, Silo refuses to terminate an active session or shared-session handoff. Container deletion does not remove managed state.

--force can terminate active shells, commands, or agents.

Manage persistent state

silo state without a subcommand behaves like silo state list.

silo state list [--json]Alias: ls
List every Silo-managed state directory with its id, scope, name, project, and host path. User-scoped entries have no project. --json uses null for that field. An empty list says No Silo managed state.
silo state delete <selector>Alias: rm
Permanently delete one unused state directory selected by its exact ID or a globally unique logical name.

Silo refuses deletion when the identity or storage path is inconsistent, the target is not a real directory, or any container still references it. There is no force option.

State deletion removes durable data recursively and cannot be undone through Silo. List state first and use the stable ID when a name is ambiguous.

Quick commands

silo <name>

Configured shortcut
silo <name> [additional arguments...]

Look up name in the effective [quick] table, append the invocation arguments, and run the result through the normal shared lifecycle.

Configure and run

[quick]
test = ["cargo", "test"]
agent = ["codex", "--model", "gpt-5"]
silo test --workspace
# Runs cargo test --workspace

silo agent --full-auto
# Runs codex --model gpt-5 --full-auto

Quick names must contain a non-whitespace character, cannot begin with -, and cannot shadow a built-in command: config, image, run, start, stop, containers, state, or help. Each command array must begin with a non-whitespace executable. Use silo run -- <command> when no shortcut exists. Quick commands use the shared lifecycle, so a running container keeps the environment, resources, and mounts it was created with.
