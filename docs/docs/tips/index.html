Field guide

Useful patterns, clear fixes.

Keep agent sessions convenient without blurring boundaries, and diagnose the effective workspace before reaching for destructive cleanup.

Build a practical agent workspace

Keep dependency and build caches private to the project. Share only the agent state that genuinely needs to follow you:

[state.project]
cargo-home = { target = "~/.cargo" }
cargo-target = { target = "./target" }

[state.user]
codex = { target = "~/.codex" }

[quick]
codex = ["codex"]
check = ["cargo", "test", "--workspace"]

This layout lets an agent reuse credentials while keeping compiled dependencies specific to one canonical project.

User state is visible to every project that enables the same logical name. Do not put project secrets there merely for convenience.

Run cooperating tools concurrently

Open separate host terminals in the same project and start each tool normally:

# Terminal one
silo run -- codex

# Terminal two
silo run -- cargo watch -x test

# Terminal three
silo run

All three sessions share the same container processes, project mount, and ephemeral filesystem. Closing one does not stop the others. Use isolated mode instead when tools should not observe each other's processes or temporary container state.

Use quick commands as a project vocabulary

Quick commands are most useful for stable entry points, not every shell expression:

[quick]
test = ["just", "test"]
lint = ["just", "lint"]
agent = ["codex", "--full-auto"]

Arguments append naturally—silo test api becomes just test api. Project commands inherit global names and replace only a same-named command. Use an empty array when the invocation itself should supply the complete command; invoking that shortcut without arguments opens the default shell.

Since Silo executes an argument vector rather than a shell string, pipes, redirects, and environment assignments need an explicit shell:

[quick]
logs = ["sh", "-lc", "just logs | tail -n 100"]

Connect to a host service

Name only the loopback service the project needs:

[forward]
postgres = { port = 5432 }
api = { port = 8080 }

Use the same IPv4 loopback ports inside the shared container:

psql -h 127.0.0.1 -p 5432
curl "http://127.0.0.1:8080/health"

Use the configured port directly: every forward keeps the same port number on the host and inside the container. Isolated runs ignore forwards with a warning; custom derivatives support them in shared mode.

Tune resources deliberately

Put stable limits in configuration and use flags for exceptional runs:

container.cpus = 4
container.memory = "6G"
silo run --cpus 8 --memory 12G -- cargo test

Resource settings apply when a container is created. If they change while the shared project container is running, Silo warns and joins it with its existing limits. The new settings apply after the container is recreated.

Enable elevation deliberately

The Silo base keeps sudo access disabled by default. Enable it persistently for a project with container.sudo = true, or opt in for one invocation:

silo run --sudo -- apt-get update

Sudo is a container creation setting. In shared mode, concurrent sessions use the same silo user and therefore share the access selected when the container was created. A changed setting applies after recreation. Use --isolated --sudo when elevation must be confined to a one-shot container. The policy applies equally to default and custom derivatives.

Choose protected paths for the workflow

Silo leaves the working tree writable while protecting existing Git metadata by default. If agents or other tools should modify Git metadata, disable the project overlays in the project file:

workspace.read_only = []

Use literal relative paths to protect additional directories, for example workspace.read_only = [".git", ".github"]. Missing entries are harmless, while absolute paths and paths that escape the project root are rejected. Existing regular files are rejected because Apple container bind mounts require directory sources.

Keep .jj writable when using Jujutsu in the container: read commands such as jj status still need metadata locks and can fail against a read-only overlay.

Inspect before cleanup

silo config path
silo config list
silo config check
silo containers
silo state

This sequence answers which files contributed, what Silo actually sees, whether the result is valid, which containers are active, and which durable directories exist.

Delete runtime containers independently from durable state:

silo containers delete my-project
silo state delete silo-state-p-<id>

Container deletion is recoverable from source and configuration. Managed state deletion removes its data permanently.

Add project-specific tools

Use a custom Dockerfile to replace Silo's default development extras while retaining its runtime behavior:

# Dockerfile.silo
FROM silo-base:latest

USER silo
RUN brew install protobuf
USER root
image.dockerfile = "./Dockerfile.silo"

[binds]
artifacts = { source = "./artifacts", target = "./artifacts", access = "read-write" }

The Dockerfile must have exactly one stage and use that literal base spelling; Silo rewrites it to an internal stage so it can never be resolved from a registry. Shared sessions, shells, /home/silo, sudo, forwarding, and project/user managed state remain available when the derivative preserves their base requirements. If you also want Silo's default agent and developer toolset, install the packages you need in your derivative; selecting a custom Dockerfile replaces the extras layer.

Troubleshooting

The selected image is not built yet

Build the currently configured image:

silo image build

If a project selects a custom Dockerfile, run the build from that project so its configuration and relative path are active. Rebuild every selected derivative after upgrading Silo; stable local image tags are trusted rather than version-negotiated at run time.

The Apple container system is unavailable

Check the runtime directly with container system status. Silo attempts to start the system for image builds and first-use paths that require it, but kernels and service failures belong to Apple's CLI.

An SSH forward cannot start

Confirm that ssh and ssh-keygen are installed on the host, rebuild the selected image after upgrading Silo, and check that the named port is free inside the container. Forwarding is intentionally unavailable for --isolated runs.

An unknown config key is ignored

Read the warning's full dotted key and file path, fix the likely typo, then run silo config check. Unknown values never participate in the effective configuration.

A bind source cannot be resolved

Confirm that the source exists and is a directory. Relative global sources resolve from the global config directory; relative project sources resolve from the project root; ~ expands from the host home. Broken symlinks are rejected.

A custom image fails its contract check

Confirm the Dockerfile has exactly one stage beginning with a literal FROM silo-base:latest, uses Docker's default backslash escape directive, and remains below 16 KiB after Silo adds its runtime base. It must leave the silo user, home, entrypoint, core helpers, and supported shells usable by the startup smoke test. ARG-based base forms are rejected. Silo leaves the previously published derivative tag available when the new candidate fails; changes outside the smoke test remain the custom image author's responsibility.

A container cannot be deleted because it is active

Let its sessions exit and retry. Use --force only when terminating those shells, commands, or agents is intentional.

Managed state is still referenced

List containers, end active sessions, and delete stopped containers that still reference the state directory. Silo intentionally offers no force-delete path for in-use durable storage.

A quick command is unknown or unusable

Inspect the effective [quick] table with silo config list. Project commands merge with global commands by name, and names cannot shadow built-ins or start with -. Assign an empty array when a shortcut should pass its invocation arguments through as the complete command.
