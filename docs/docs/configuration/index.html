Reference

Configuration, layer by layer.

Every setting is optional. Start with the defaults, keep personal preferences global, and add a small project file only where the workspace needs to differ.

Configuration files

LayerLocationPurpose
Built-inEmbedded in SiloUsable defaults for every option
Global$XDG_CONFIG_HOME/silo/config.tomlUser-wide preferences
Global fallback~/.config/silo/config.tomlUsed when XDG_CONFIG_HOME is unset, empty, or relative
Project<project>/.silo.tomlProject-specific overrides and an explicit root marker
Invocation--cpus, --memory, --sudoContainer overrides for one run

Precedence is built-in defaults → global file → project file → CLI flags. A missing global file is initialized from Silo's commented starter template when a config-consuming command first loads it. If no home directory can be determined, Silo continues with built-in defaults.

silo config default  # print the starter file
silo config path     # list active files
silo config list     # print the merged result
silo config check    # validate the merged result

How layers merge

Most project values replace the same global value only when present. Omitted values inherit. Four collections have explicit rules:

  • Forwards merge by name and field. A project may change only enabled or port on an inherited forward. A new project forward must provide port.
  • Binds and state merge by name and field. A project may retarget or disable an inherited entry within its existing category. Reusing a name under a different bind or state category is an error.
  • Read-only paths replace as a collection. A project workspace.read_only array replaces the global array; an empty array disables inherited read-only workspace overlays without changing bind permissions.
  • Quick commands merge by name. A project may add commands or replace the complete argument array for an inherited name. An empty project table changes nothing; an empty array clears that name's fixed command prefix.

A project can inherit a global custom Dockerfile or replace it with another path, but there is no project-level sentinel that resets a global custom derivative back to Silo's default extras image.

Complete example

# Every setting shown here is optional.
# Use exactly one stage starting with a literal FROM silo-base:latest.
# image.dockerfile = "containers/Dockerfile"
container.cpus = 4
container.memory = "6G"
container.sudo = false
shell = "zsh"
workspace.read_only = [".git"]

[forward]
postgres = { port = 5432, enabled = true }
redis = { port = 6379, enabled = false }

[binds]
docs = { source = "~/Documents/docs", target = "~/docs", access = "read-only" }
output = { source = "./output", target = "./output", access = "read-write" }

[state.project]
cargo = { target = "~/.cargo" }
cargo-target = { target = "./target" }

[state.user]
codex = { target = "~/.codex" }

[quick]
test = ["cargo", "test"]
agent = ["codex"]

Do not copy the whole example by default. Include only the settings that express an actual workspace decision.

Image and container options

KeyType and defaultBehavior
image.dockerfilePath; default extrasBuild this single-stage Dockerfile as the tool layer above a literal FROM silo-base:latest. Relative paths resolve from the directory containing the configuration file.
container.cpusPositive integer; runtime defaultPasses the CPU limit to containers at creation time.
container.memoryNon-empty string; runtime defaultPasses Apple's accepted memory syntax, such as 4G.
container.sudoBoolean; falseGrants the base image's silo user passwordless sudo access in default and custom derivatives.
shellbash, zsh, fish, or nu; automaticSelects an interactive shell supplied by the base image. Automatic mode mirrors a supported host $SHELL and otherwise uses Zsh.
workspace.read_onlyRelative directory array; [".git"]Overlays each existing workspace directory read-only. Paths are literal, may be nested, and must remain inside the project root; use [] to disable these overlays.

CPU, memory, sudo access, and resolved read-only paths participate in shared-container identity. A changed value is applied when a stopped workspace is recreated. If the workspace is already running, Silo warns and joins it with its existing creation settings. Missing read-only paths are ignored; workspace.read_only = [".git", ".github"] additionally protects a project directory, while workspace.read_only = ["."] protects the entire project.

The base image contains the sudo command, but its locked silo user cannot elevate unless container.sudo = true or silo run --sudo enables passwordless access.

Custom Dockerfile contract

FROM silo-base:latest

USER silo
RUN brew install protobuf
USER root

The Dockerfile must contain exactly one stage, and its FROM silo-base:latest spelling must be literal; build-argument forms are rejected. Silo composes that reference into the generated Dockerfile as an internal stage, so silo-base:latest is never sent to a registry resolver. Because the embedded base uses backslash continuations, derivatives must keep Docker's default backslash escape directive. Apple's current builder also requires the composed Dockerfile to remain below 16 KiB. The configured directory remains the build context, including a Dockerfile-specific .dockerignore file. External images remain available through instructions such as COPY --from=registry.example/tools:latest.

Before publication, Silo starts the candidate through its normal entrypoint and checks the silo identity, home, core lifecycle helpers, and supported shells. This is intentionally a small compatibility check. A custom Dockerfile is trusted project input, and its author is responsible for permissions, links, packages, and other root-level changes that may break Silo behavior.

Do not add .jj when Jujutsu commands need to run in the container. Even inspection commands such as jj status acquire locks and may update Jujutsu metadata, so a read-only .jj overlay prevents normal operation.

Apple container supports only directories as bind-mount sources. An existing workspace.read_only entry that resolves to a regular file, such as AGENTS.md, prevents container creation with a clear error. Protect its containing directory or use a different enforcement mechanism for individual files.

Host loopback forwards

[forward]
postgres = { port = 5432 }
web_api = { port = 8080, enabled = true }
FieldRequirement
NameStarts with a lowercase ASCII letter; remaining characters are lowercase letters, digits, or _.
portHost loopback TCP port from 1024 through 65535.
enabledOptional boolean; defaults to true.

In a shared container, each configured port is available on the same IPv4 loopback port, so the example services are reachable at 127.0.0.1:5432 and 127.0.0.1:8080.

Silo establishes an authenticated SSH reverse tunnel for only the named ports. Each guest listener binds to 127.0.0.1 and connects to the same 127.0.0.1 port on the host; forwarding does not expose other host services.

Forwarding requires the shared lifecycle. Silo warns and ignores enabled forwards for --isolated runs, regardless of which derivative image is selected.

Host binds

[binds]
reference = { source = "~/Documents/reference", target = "~/reference", access = "read-only" }
artifacts = { source = "./artifacts", target = "./artifacts", access = "read-write" }
disabled = { enabled = false }
FieldDefaultBehavior
enabledtrueDisabled entries may omit source and target and are not resolved at run time.
sourceRequired when enabledAn existing host directory. ~ expands from host home; relative file paths resolve from the containing config's base.
targetRequired when enabledDestination inside the container.
accessRequired when enabledExplicitly selects read-only or read-write.

Sources are canonicalized when a session starts. Missing paths, broken symlinks, and non-directory sources fail loudly instead of creating an unexpected bind.

Managed state

[state.project]
dependencies = { target = "~/.cache/dependencies" }
build = { target = "./target" }

[state.user]
agent-state = { target = "~/.agent" }
disabled = { enabled = false }

State entries accept only target and optional enabled. Silo creates private writable host storage:

  • Project state is keyed by canonical project path and entry name.
  • User state is keyed by entry name and is intentionally reused across this user's projects.

Bind and state names must start with an ASCII letter or digit and then contain only letters, digits, _, or -. One logical name cannot appear in more than one bind or state category, including across global and project configuration.

Target path rules

FormResolves toExample
./…The mounted project working directory./target
~/…/home/silo in every compatible image~/.cargo
/…An absolute container path/output

Targets must be non-empty UTF-8, may not contain commas, equals signs, or newlines, and may not contain ... Mounts may not replace /home/silo, Silo's lifecycle helper files, or its runtime state and configuration directories. These focused checks prevent direct startup breakage without trying to validate the full filesystem of a trusted custom image.

Runtime mounts are ordered from parent to child. If two configured entries resolve to the same target, the deterministic later entry wins and Silo emits a warning.

Quick commands

[quick]
check = ["just", "check"]
cx = ["codex", "--model", "gpt-5"]

Each key is the token typed after silo. Each value is a TOML array containing the executable and any fixed arguments. Invocation arguments are appended without shell interpolation.

Global and project quick commands merge by name. A project array replaces only the inherited command with the same name. An empty array creates a pass-through shortcut: invocation arguments become the complete command, while invoking the shortcut without arguments opens the default shell.

Names beginning with - or colliding with built-in commands are unreachable; Silo warns and asks you to rename them. Built-in subcommands always win.

Validation and diagnostics

silo config check validates the effective configuration without creating a container. It checks:

  • TOML structure and field types.
  • CPU, memory, forward names, ports, bind and state names, and path syntax.
  • Required fields for enabled binds and state entries.
  • The configured Dockerfile's existence and file type.
  • Custom-image and home-relative bind incompatibilities.

Resolved Dockerfile and bind-source host paths must be valid UTF-8. Bind source existence is checked again at silo run, because the filesystem can change after validation. Unknown config keys are warnings rather than hard errors, with both the file and ignored key named.
