Reference

Configuration, layer by layer.

Every setting is optional. Start with the defaults, keep personal preferences global, and add a small project file only where the workspace needs to differ.

Configuration files

LayerLocationPurpose
Built-inEmbedded in SiloUsable defaults for every option
Global$XDG_CONFIG_HOME/silo/config.tomlUser-wide preferences
Global fallback~/.config/silo/config.tomlUsed when XDG_CONFIG_HOME is unset, empty, or relative
Project<project>/.silo.tomlProject-specific overrides and an explicit root marker
Invocation--cpus, --memoryResource overrides for one run

Precedence is built-in defaults → global file → project file → CLI flags. A missing global file is initialized from Silo's commented starter template when a config-consuming command first loads it. If no home directory can be determined, Silo continues with built-in defaults.

silo config default  # print the starter file
silo config path     # list active files
silo config list     # print the merged result
silo config check    # validate the merged result

How layers merge

Most project values replace the same global value only when present. Omitted values inherit. Three collections have explicit rules:

  • Forwards merge by name and field. A project may change only enabled or port on an inherited forward. A new project forward must provide port.
  • Mounts merge by name and field. A project may retarget or disable an inherited mount. Moving the same name to another category resets category-specific fields before applying the project entry.
  • Quick commands replace as a collection. If the project contains a [quick] table, it replaces the global table. An empty project table clears all global quick commands.

A project can inherit a global custom Dockerfile or replace it with another path, but there is no project-level sentinel that resets a global custom image back to the built-in image.

Complete example

# Every setting shown here is optional.
# image.dockerfile = "/absolute/path/to/Dockerfile"
container.cpus = 4
container.memory = "6G"
shell = "zsh"
read_only_git = true

[forward]
postgres = { port = 5432, enabled = true }
redis = { port = 6379, enabled = false }

[mounts.host]
docs = { source = "~/Documents/docs", target = "~/docs" }
output = { source = "./output", target = "./output", writable = true }

[mounts.project]
cargo = { target = "~/.cargo" }
cargo-target = { target = "./target" }

[mounts.shared]
codex = { target = "~/.codex" }

[quick]
test = ["cargo", "test"]
agent = ["codex"]

Do not copy the whole example by default. Include only the settings that express an actual workspace decision.

Image and container options

KeyType and defaultBehavior
image.dockerfilePath; built-in imageBuild this Dockerfile as silo:latest. Project-relative paths resolve from the project root. Use an absolute path in the global file.
container.cpusPositive integer; runtime defaultPasses the CPU limit to containers at creation time.
container.memoryNon-empty string; runtime defaultPasses Apple's accepted memory syntax, such as 4G.
shellbash, zsh, fish, or nu; automaticSelects the interactive shell in the built-in image. Automatic mode mirrors a supported host $SHELL and otherwise uses Zsh.
read_only_gitBoolean; trueOverlays the real project .git directory read-only when it resolves safely inside the project.

CPU and memory values participate in shared-container identity. A changed limit causes the next run to replace a mismatched stopped workspace or coordinate safe replacement when possible.

Host loopback forwards

[forward]
postgres = { port = 5432 }
web_api = { port = 8080, enabled = true }
FieldRequirement
NameStarts with a lowercase ASCII letter; remaining characters are lowercase letters, digits, or _.
portHost loopback TCP port from 1024 through 65535.
enabledOptional boolean; defaults to true.

Inside the session, each enabled name becomes an uppercase environment prefix. The example supplies SILO_POSTGRES_HOST, SILO_POSTGRES_PORT, SILO_WEB_API_HOST, and SILO_WEB_API_PORT.

The configured port is where the service listens on the host, so PostgreSQL may stay on host localhost:5432. Inside the container, connect to $SILO_POSTGRES_HOST:$SILO_POSTGRES_PORT; container-local localhost is not the host.

Silo forwards only the named host loopback ports. It creates a private project network and relays traffic through bounded listeners rather than exposing every host service.

Host mounts

[mounts.host]
reference = { source = "~/Documents/reference", target = "~/reference" }
artifacts = { source = "./artifacts", target = "./artifacts", writable = true }
disabled = { enabled = false }
FieldDefaultBehavior
enabledtrueDisabled entries may omit source and target and are not resolved at run time.
sourceRequired when enabledAn existing host directory. ~ expands from host home; relative file paths resolve from the containing config's base.
targetRequired when enabledDestination inside the container.
writablefalseHost mounts are read-only unless writes are explicitly enabled.

Sources are canonicalized when a session starts. Missing paths, broken symlinks, and non-directory sources fail loudly instead of creating an unexpected mount.

Project and shared mounts

[mounts.project]
dependencies = { target = "~/.cache/dependencies" }
build = { target = "./target" }

[mounts.shared]
agent-state = { target = "~/.agent" }
disabled = { enabled = false }

Managed entries accept only target and optional enabled. Silo creates private writable host storage:

  • Project storage is keyed by canonical project path and mount name.
  • Shared storage is keyed by mount name and is intentionally reused across projects.

Mount names must start with an ASCII letter or digit and then contain only letters, digits, _, or -. One name cannot appear in more than one mount category in the same file.

Target path rules

FormResolves toExample
./…The mounted project working directory./target
~/…/home/silo in the built-in image~/.cargo
/…An absolute container path/output

Targets must be non-empty UTF-8, may not contain commas, equals signs, or newlines, and may not use .. to escape a relative anchor. Custom images reject home-relative host targets because they do not define Silo's /home/silo contract.

Nested mounts are ordered from parent to child. If two entries resolve to the same target, the deterministic later entry wins and Silo emits a warning.

Quick commands

[quick]
check = ["just", "check"]
cx = ["codex", "--model", "gpt-5"]

Each key is the token typed after silo. Each value is a TOML array containing the executable and any fixed arguments. Invocation arguments are appended without shell interpolation.

Names beginning with - or colliding with built-in commands are unreachable; Silo warns and asks you to rename them. Built-in subcommands always win.

Validation and diagnostics

silo config check validates the effective configuration without creating a container. It checks:

  • TOML structure and field types.
  • CPU, memory, forward names, ports, mount names, and path syntax.
  • Required fields for enabled mounts.
  • The configured Dockerfile's existence and file type.
  • Custom-image and home-relative mount incompatibilities.

Host mount source existence is checked again at silo run, because the filesystem can change after validation. Unknown config keys are warnings rather than hard errors, with both the file and ignored key named.
