Under the hood

How Silo works.

Silo is a focused host-side coordinator. It delegates virtual machines and OCI images to Apple's runtime while making project identity, concurrent sessions, storage, and host access deterministic.

From command to workspace

  1. Discover. Canonicalize the current directory and select a .silo.toml marker, Git root, or the current directory itself.
  2. Configure. Load built-in defaults, global TOML, and the project TOML; warn about unknown or unreachable entries; then apply invocation resource flags.
  3. Validate. Resolve the lifecycle, image contract, named mounts, configured Git metadata access, resource limits, and enabled forwards.
  4. Prepare. Confirm the image/runtime state and establish managed storage or a forwarding lease where needed.
  5. Run. Reuse or create the shared project container, or create a one-shot isolated container, then attach the requested shell or command.
  6. Clean up. Restore the terminal, release session and forwarding leases, and remove isolated runtime resources.

Silo has no persistent host daemon. The forwarding broker is a short-lived internal helper started only when forwarding is active and exits after its leases become idle.

Identity and ownership

A shared container name begins with silo- and ends with the first 24 hexadecimal characters of a SHA-256 digest of the canonical project path. The stable name makes concurrent Silo processes converge on the same workspace.

Silo also writes ownership, schema, project, project-root, lifecycle, and specification labels. Before it starts, stops, replaces, or deletes a resource, it inspects those labels and rejects anything that does not match the expected identity.

A matching name alone is never sufficient evidence that Silo owns a container or network.

Management commands inventory only unambiguously Silo-owned resources. They report malformed entries as warnings rather than guessing.

The container specification

Shared-container reuse depends on more than its project ID. Silo hashes creation-time inputs into a specification label, including:

  • The image digest and lifecycle.
  • Host user and group IDs.
  • Project root and working directory.
  • Git overlay, named mount sources, targets, and access modes.
  • Forward network, CPU count, memory, and creation command.

If the running or stopped container does not match the desired specification, Silo coordinates replacement rather than silently reusing the wrong environment. Image changes during creation are detected and retried within a bounded window.

Ephemeral state inside the old container is lost on replacement. The source tree and configured managed mounts are host-backed and remain available.

Shared session handoff

The built-in image runs a small Silo supervisor as PID 1. Before starting an arbitrary user command, the host waits for an explicit guest readiness marker and reserves a session token through a safe helper.

The reservation closes a subtle race: without it, the supervisor could decide the container was idle after host inspection but just before the command attached. Only the reservation helper is retried; Silo never replays the user's command automatically.

Once attached, a guest wrapper owns the session lease for the command and its children. The supervisor observes reservations and active leases and exits only when both reach zero. This allows shells, tests, and agents to overlap without one process shutting down another's container.

When Silo receives an interrupt, termination, hangup, or quit signal, it forwards the signal to the attached runtime process, waits for cleanup, and restores the host terminal state.

Isolated lifecycle

An isolated run creates a unique container, starts it in the foreground, forwards relevant signals, and deletes the container after the child exits. Interrupted or failed creation paths also attempt cleanup.

The built-in isolated mode uses the same project mount, Git overlay, named host mounts, and managed storage as shared mode. Its container filesystem is disposable, but configured mount state is not.

Custom images use the same one-shot host lifecycle but preserve their own image-defined command and user. Silo skips private managed mounts and rejects ~/ host targets because those features depend on the built-in image's user contract.

Mount resolution and storage

Enabled host sources are expanded, canonicalized, and verified as directories at run time. Managed mounts receive deterministic host paths and opaque IDs. Silo creates their parent directories with private permissions, guards mutations with file locks, and stores project-path metadata beside project mounts.

Before using or deleting managed state, Silo checks that directories are real rather than symlinks, ownership metadata matches the expected project, and the derived ID/path are consistent. Deletion additionally asks the runtime whether any container still references the directory.

Mounts are sorted from shallower to deeper targets so nested overrides are deterministic. A later duplicate target wins, and potentially surprising overlaps—especially writable paths under the read-only Git target—produce warnings.

Git metadata overlay

When enabled, Silo canonicalizes <project>/.git and mounts it separately at the corresponding path inside the writable project tree. It applies the overlay only when the resolved path remains inside the canonical project root; a missing directory or a symlink escaping the project is not mounted.

This is a focused guardrail, not a full sandbox policy. Tools can still edit source files, and another explicitly writable mount can overlap the protected destination. Silo warns about known overlap but preserves the user's configured mount order.

Host loopback forwarding

A container cannot reach a service bound only to the host's 127.0.0.1 through normal container networking. For each project with enabled forwards, Silo:

  1. Checks that Apple's container runtime is at least version 1.2.1.
  2. Creates or validates a labeled, project-specific IPv4 network.
  3. Acquires relay listeners from a per-user local broker.
  4. Limits accepted relay sources to leased project-network subnets.
  5. Passes the network gateway and leased port into the session environment.
[forward]
postgres = { port = 5432 }

# Available inside the container:
SILO_POSTGRES_HOST=<project-network-gateway>
SILO_POSTGRES_PORT=<leased-relay-port>

The relay connects each accepted request to 127.0.0.1:5432 on the host. Listener ports are implementation details, so programs should always read both generated variables rather than assuming the configured destination port.

The broker caps concurrent relay work, shares listeners safely across active sessions, and removes idle networks only after their leases close. Startup and cleanup are serialized per project to avoid deleting a network while another session is acquiring it.

Runtime boundary

Apple's container CLI owns Linux kernels, image storage, networking, VM execution, and low-level mount behavior. Silo owns only the resources carrying its validated labels and delegates commands through the CLI.

Image building is the exception where Silo intentionally treats Apple's user-global builder and dangling build images as disposable storage. Container and mount management remains ownership-scoped and conservative.
