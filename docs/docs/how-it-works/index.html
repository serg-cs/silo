Under the hood

How Silo works.

Silo is a focused host-side coordinator. It delegates virtual machines and OCI images to Apple's runtime while making project identity, concurrent sessions, storage, and host access deterministic.

From command to workspace

  1. Discover. Canonicalize the current directory and select a .silo.toml marker, the nearest Git or Jujutsu root, or the current directory itself.
  2. Configure. Load built-in defaults, global TOML, and the project TOML; warn about unknown or unreachable entries; then apply invocation resource flags.
  3. Validate. Resolve the lifecycle, image contract, binds, managed state, configured read-only workspace paths, container settings, and enabled forwards.
  4. Prepare. Confirm the image/runtime state and establish managed storage and SSH forwarding assets where needed.
  5. Run. Reuse or create the shared project container, or create a one-shot isolated container, then attach the requested shell or command.
  6. Clean up. Restore the terminal, release the session lease, and remove isolated runtime resources.

Silo has no persistent host daemon. When forwarding is active, the host SSH master remains connected only for the lifetime of the shared container and exits when that container stops.

Identity and ownership

A shared container name begins with silo- and ends with the first 24 hexadecimal characters of a SHA-256 digest of the canonical project path. The stable name makes concurrent Silo processes converge on the same workspace.

Silo also writes ownership, schema, project, project-root, lifecycle, and specification labels. Before it starts, stops, replaces, or deletes a resource, it inspects those labels and rejects anything that does not match the expected identity.

A matching name alone is never sufficient evidence that Silo owns a container or network.

Management commands inventory only unambiguously Silo-owned resources. They report malformed entries as warnings rather than guessing.

The container specification

Shared-container reuse depends on more than its project ID. Silo hashes creation-time inputs into a specification label, including:

  • The image digest and lifecycle.
  • Host user and group IDs.
  • Project root and working directory.
  • Read-only workspace overlays, bind and state sources, targets, and access modes.
  • Forwarding SSH assets and ports, CPU count, memory, and creation command.

If the running or stopped container does not match the desired specification, Silo coordinates replacement rather than silently reusing the wrong environment. Image changes during creation are detected and retried within a bounded window.

Ephemeral state inside the old container is lost on replacement. The source tree, binds, and configured managed state are host-backed and remain available.

Shared session handoff

The built-in image runs a small Silo supervisor as PID 1. Before starting an arbitrary user command, the host waits for an explicit guest readiness marker and reserves a session token through a safe helper.

The reservation closes a subtle race: without it, the supervisor could decide the container was idle after host inspection but just before the command attached. Only the reservation helper is retried; Silo never replays the user's command automatically.

Once attached, a guest wrapper owns the session lease for the command and its children. The supervisor observes reservations and active leases and exits only when both reach zero. This allows shells, tests, and agents to overlap without one process shutting down another's container.

When Silo receives an interrupt, termination, hangup, or quit signal, it forwards the signal to the attached runtime process, waits for cleanup, and restores the host terminal state.

Isolated lifecycle

An isolated run creates a unique container, starts it in the foreground, forwards relevant signals, and deletes the container after the child exits. Interrupted or failed creation paths also attempt cleanup.

The built-in isolated mode uses the same project mount, read-only overlays, binds, and managed state as shared mode. Its container filesystem is disposable, but configured state is not.

Custom images use the same one-shot host lifecycle but preserve their own image-defined command and user. Silo skips private managed state and rejects ~/ bind targets because those features depend on the built-in image's user contract.

Mount resolution and storage

Enabled bind sources are expanded, canonicalized, and verified as directories at run time. Managed state receives deterministic host paths and opaque IDs. Silo creates parent directories with private permissions, guards mutations with file locks, and stores project-path metadata beside project-scoped state.

Before using or deleting managed state, Silo checks that directories are real rather than symlinks, ownership metadata matches the expected project, and the derived ID/path are consistent. Deletion additionally asks the runtime whether any container still references the directory.

Runtime mounts are sorted from shallower to deeper targets so nested overrides are deterministic. A later duplicate target wins, and read-write binds or state at or below configured read-only workspace paths produce warnings.

Read-only project overlays

For each configured relative path, Silo canonicalizes the host directory and mounts it separately at the corresponding path inside the writable project tree. It applies an overlay only when the resolved path remains inside the canonical project root; a missing path, broken symlink, or symlink escaping the project is not mounted. Existing regular files fail resolution because Apple container does not support them as bind-mount sources.

This is a focused guardrail, not a full sandbox policy. Tools can still edit source files, and an explicit read-write bind can overlap the protected destination. Silo warns about known overlap but preserves deterministic runtime mount order.

Host loopback forwarding

A container cannot reach a service bound only to the host's 127.0.0.1 through normal container networking. In the built-in shared mode, Silo:

  1. Generates or reuses a managed client identity and a project-specific SSH host identity.
  2. Mounts only the guest host key and a restricted authorized_keys file into the container.
  3. Waits for the container's IPv4 address and its restricted SSH server.
  4. Starts or reuses one authenticated SSH master with a reverse tunnel for each named port.
  5. Binds every guest listener to 127.0.0.1 and targets the same 127.0.0.1 port on the host.
[forward]
postgres = { port = 5432 }

# Available in the built-in shared container:
127.0.0.1:5432
SILO_POSTGRES_PORT=5432

The SSH client uses Silo's managed identity, exact host-key verification, and no ambient SSH configuration or agent. The guest account cannot open a shell, allocate a terminal, forward an agent, or listen on an unconfigured port.

Custom images and isolated runs keep a narrower contract: Silo warns, ignores enabled forwards, and supplies no forward environment variables.

The broker caps concurrent relay work, shares listeners safely across active sessions, and removes idle networks only after their leases close. Startup and cleanup are serialized per project to avoid deleting a network while another session is acquiring it.

Runtime boundary

Apple's container CLI owns Linux kernels, image storage, networking, VM execution, and low-level mount behavior. Silo owns only the resources carrying its validated labels and delegates commands through the CLI.

Image building is the exception where Silo intentionally treats Apple's user-global builder and dangling build images as disposable storage. Container and managed-state operations remain ownership-scoped and conservative.
