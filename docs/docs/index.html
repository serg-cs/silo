Documentation

Start with the project.

Silo turns the current project into the unit of isolation. Build the image once, open a session, and add only the state and host access that your tools actually need.

Requirements

Silo runs on Apple's container CLI. Its upstream supported environment is an Apple silicon Mac running macOS 26. Consult the official runtime requirements for current platform details.

Host loopback forwarding additionally requires the host ssh and ssh-keygen commands. It is available to compatible images in the shared lifecycle.

Install from source

Install Rust 1.91 or newer with Cargo, then build and install the latest Silo source directly from GitHub:

cargo install --git https://github.com/serg-cs/silo --locked

If you already have the repository checked out, install that checkout instead:

cargo install --path . --locked

Cargo places the executable in $CARGO_HOME/bin, or ~/.cargo/bin by default. Add that directory to PATH if your shell cannot find silo, then verify the installation:

silo --version

After upgrading Silo, run silo image build again. Silo trusts its locally published image tags and does not run older images through a cross-version compatibility path.

Your first session

Build Silo's images before the first run. The runtime base supplies every feature Silo needs; the default extras layer adds coding agents, browser tooling, language runtimes, and common development utilities.

silo image build

Move into a Git or Jujutsu repository—or any working directory—and open a shell:

cd ~/code/my-project
silo run

Silo discovers a project root, mounts it read-write as the container's working directory, and starts a shared container. The host user and group IDs are mirrored into every Silo-compatible image so files remain usable on both sides.

Run a single command by placing it after the required -- separator:

silo run -- cargo test
silo run -- codex --model gpt-5

Open another terminal and run silo run again to join the same project container. The shared container remains alive until every active session exits.

Add a project configuration

A .silo.toml file marks an explicit project root and adds project-specific settings. Start small:

[state.project]
cargo = { target = "~/.cargo" }
cargo-target = { target = "./target" }

[quick]
test = ["cargo", "test"]
agent = ["codex"]

Validate and inspect the result before running it:

silo config check
silo config list

You can now write silo test --workspace. Silo expands it to cargo test --workspace inside the container. Project-managed Cargo state survives automatic container removal but remains private to this project.

Choose the lifecycle

ModeUse it forLifecycle
silo runNormal shells, commands, and concurrent agentsStable per-project container; stops after the last session
silo run --isolatedClean-room checks and one-off untrusted workNew foreground container; deleted when the session ends
Custom DockerfileA project-defined tool layerShared by default; isolated only with --isolated

Both lifecycles mount the project and can use configured binds and managed state. Because every selected image inherits the same Silo base, shell selection, sudo, forwarding, shared sessions, and storage work consistently with default and custom tool layers.
