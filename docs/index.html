Boundaries without busywork.

Silo wraps Apple's native container runtime with a project model built for real development sessions. Source stays close, durable state is deliberate, and the disposable parts disappear when the work is done.

01

Agent-ready image

Start with popular coding agents, shells, browser tooling, language runtimes, and everyday CLI utilities in the default extras image.

02

One project, one workspace

A canonical project path creates a stable identity, working directory, and shared container that later sessions can reuse.

03

Concurrent by design

Run a shell, an agent, and a test command together. Session leases prevent the shared container from stopping underneath active work.

04

Durable state, chosen explicitly

Keep caches per project, share selected credentials across projects, or expose host directories with read-only access by default.

05

Shared or isolated

Reuse the project container for normal work, or start a one-shot environment when a task should have a clean runtime boundary.

06

Explicit host ports

Allow only the Mac loopback ports needed for databases and local APIs, then reach them on the same 127.0.0.1 ports inside any compatible shared workspace.

A small mental model.

Build the workspace image, enter a project, and run the tools you need. Configuration stays layered and inspectable instead of becoming another environment manager.

Build once

silo image build produces the runtime base, then adds either Silo's agent-ready extras or the custom Dockerfile selected in configuration.

Work together

silo run opens a shared shell. Run additional commands or agents concurrently against the same mounted project.

Leave cleanly

The shared container stops after its last session. Managed state keeps only the caches, credentials, and tool data you asked Silo to retain.
